## Tested behavior and independent review

- Test-first HTTP verification reproduced the old creator-only callback returning `/` when the initiating page requested administration. The callback now uses the server-side attempt's fixed destination. Unrecognised destinations fall back to the home page. The HTTP test checked that callback query parameters could not change the stored destination.
- Chromium exercised `/admin` through a real disposable OIDC exchange and PostgreSQL role lookup. A workspace owner without a platform operations role saw no administration data and received 403 from both health and incidents APIs. A platform viewer could read health and the exact redacted incident record and received 403 for an incident write.
- Removing the viewer's operations role denied an active session and cleared the console after reload. Restoring the synthetic role made the console visible again. Sign-out then cleared it, returned to `/admin` and revoked the session. Both an anonymous request and replay of the old credential received 401.
- Independent standards and spec reviews found no application source blocker. They identified that rendering could hide a leaked endpoint, an incident row alone could miss extra response fields, and a cleared cookie alone did not prove revocation. The final browser assertions cover both endpoints, exact response shape, role removal and server-side revocation while proving sign-out clears a visible console.
- The console is a snapshot. A role change blocks subsequent requests immediately, and a reload clears previously displayed data. The existing operations role model, schema, detached development entry point and OIDC tenant configuration are used. Disabling University sign-in uses the existing deployment configuration.
