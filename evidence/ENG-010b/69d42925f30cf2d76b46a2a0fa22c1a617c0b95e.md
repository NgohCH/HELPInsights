## Scope and assertions

- The running API accepts only GET for disposal preview. It requires the
  survey workspace membership and explicit retention appointment, and
  exposes only disposition and deadlines. The denied owner receives
  `code`, `message`, and `requestId` with no eligibility details.
  No session returned 401, a foreign membership returned 404, and
  POST returned 405. The preview left the tombstone ledger empty.
- The runtime migration adds the preview and a protected ledger. The
  runtime and export worker database roles have no tombstone insert
  grant. The application image excludes the fixture SQL and the stack's
  application database has no disposal fixture schema.
- Destructive tests cloned synthetic fixture data into two temporary
  databases with random names inside the labeled local Compose project.
  The SQL entry point checks the database name, exact project, marker and
  survey binding before mutation. Wrong project, marker and survey were
  refused. Held, future-deadline and queued-export surveys preserved all
  six checked row types.
- Under the export worker role, the test held a queued job with the
  existing `FOR UPDATE SKIP LOCKED` claim. The concurrent fixture
  disposal timed out waiting on the job with SQLSTATE `55P03`.
  The source worker keeps the job queued and locked until it commits
  a completion, retry or failure. The test did not run a background
  worker against either restored test database.
- An injected failure during version deletion rolled back preceding
  derivative and content changes and wrote no ledger entry. Two
  concurrent requests on an eligible fixture returned one `disposed`
  and one `already_disposed`. Survey, version, response, distribution,
  stored export and download audit rows were all absent. A sequential
  retry kept the same tombstone, containing survey ID, workspace ID
  and disposal time only.
- A restore from the pre-disposal archive initially contained the old
  survey and stored export. The wrong workspace replay was denied and
  kept the data intact. The fixture then applied the record from the
  verified source ledger, removed the same data, and preserved the
  original disposal timestamp. No app or worker was started against
  the restore database.
- Chromium covered existing operations and survey create, publish,
  respond, restart, reporting and JASP export. The read-only preview
  has no new UI.

## Independent review and release boundary

The integration reviewer confirmed least privilege, workspace scoping
and the hold-aware fixture boundary. The review led to exact forbidden
response assertions, a running export lock check and documented failed
restore escalation. A failed or mismatched restore must remain isolated
from application traffic and be escalated for manual reconciliation.

Production scheduling, outbound notices, approved timing for remaining
or recently completed exports, external derivative cleanup, ledger
retention, and trusted pre-traffic replay orchestration remain open.
The fixture implements none of those production tasks. Keep any ledger
records through rollback. A prior runtime requires an exact matching
schema ledger or a compatible build. None of these checks used shared
or production data.
