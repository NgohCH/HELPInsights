## Observed behaviour

The presenter opened questions in published order and could explicitly close one. Two concurrent requests with the same expected ballot opening revision, participant, idempotency key and choice returned the same original server receipt and one row. An invalid option returned 422. A foreign room credential, presenter credential or expired guest could not vote. Changed payload, second key, stale opening revision, paused room, closed question and ended room produced conflicts for new ballots. Direct SQL confirmed zero ordinary survey responses and no direct vote SELECT or UPDATE grant for the application runtime role.

The initial presenter and mobile guest Chromium sockets received the opened question. The guest received its own durable voted flag, and the presenter received the five-vote turnout cohort. Exact option counts first appeared after closure. Two integration cases verified suppression for a minority of one and for a single nonvoter. The restricted database reader returned NULL without an explicit role. The guest payload carried neither aggregate turnout nor results.

The single-room contention run used 50 distinct synthetic guest capabilities and 51 local WebSocket connections including the presenter. One simultaneous HTTP ballot per guest completed in 64 ms, and presenter's cohort plus all 50 private guest receipts converged by 95 ms from the start of that wave. After closure the presenter received the aggregate of 50. Direct PostgreSQL returned 25 durable votes per option and 50 distinct voters. These figures cover the local run with Node WebSocket clients and one single-process app. The separate browser test used one presenter, one mobile Chromium guest and four API fixture votes.

## Independent review and remaining scope

The integration owner challenged differencing of a live tally and room/guest lock order. The implementation publishes option totals only when casting permanently closes, and applies the existing survey-style minimum cell size of five for positive categories and the nonvoter complement. Each vote acquires the room share lock before locking and rechecking the guest. Future revocation and retention code should acquire room then guest when locking both. Archived aggregates may need stable release snapshots when later retention changes the population.

One intermediate full run exposed an inherited export worker crash on a PostgreSQL restart. The checked-out PostgreSQL Client emitted unhandled `ECONNRESET`, and later browser fixtures detected the absent worker. Evidence is retained in `runtime-evidence/helpinsights-test-3fc5a351583b.log`. It was reported to the integration owner for separate recovery work. The final voting rerun passed the unchanged browser and restore regressions.

This branch covers a single-process untimed Live Poll with one vote per anonymous guest capability. Rejoining while a lobby is open can create a distinct capability. The wider acceptance gates still include formal assessment identity and scoring, authoritative question deadlines, multi-instance fan-out, historical results/export and retention, vote abuse controls, accessibility review and production activation. The activation flag defaults off. Migration 008 is additive to existing lobbies and should be rolled forward to preserve votes.
