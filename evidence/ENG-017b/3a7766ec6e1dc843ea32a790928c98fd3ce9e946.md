## Observed behavior

- A synthetic recovery already in the redacted worker ledger appeared once
  in the in-app list for explicit operators when the development
  flag was on. The paired detection and a manual recovery were excluded.
  A viewer and ordinary workspace user received 403. Unauthenticated
  requests received 401. Default configuration returned 404 for the list
  and receipt endpoints.
- Concurrent requests for the same receipt returned the same timestamp.
  SQL showed a single receipt with the verified operator ID. The second
  operator still saw an open notice, and app-role SQL returned no rows
  for the first operator's receipt. Direct application writes and worker
  function execution were denied. Revocation removed both access to the
  receipt and the ability to acknowledge.
- Chromium opened Operations with the viewer and operator fixtures, then
  acknowledged the visible recovery with the keyboard. After reload,
  reopening Operations under the same operator showed **Acknowledged**.
- A database created before the receipt migration held a legacy manual
  incident and a worker recovery. Applying the remaining migration allowed
  the operator to acknowledge the pre-existing recovery. A custom archive
  restored the receipt's incident ID, operator ID and exact timestamp
  alongside the existing incident records.

## Independent review and remaining scope

An independent reviewer verified that the application derives receipt
ownership from the verified actor, the database projects only recovered
export episodes, and row security restricts receipt reads to the current
operator. Acknowledgement holds a membership row lock through insertion.
The primary key and conflict handling preserve the timestamp on retries.
Reads use current statement snapshots. A read that started before a role
revocation can complete on its earlier snapshot. A later authenticated
read sees the new membership state.

This test-enabled inbox shows at most 100 recent recovery episodes.
Operators who are newly appointed see eligible history and an operator who
is reappointed sees their existing receipts. A release policy is still
needed for the duration and lifecycle of incident and receipt history,
assignment, escalation, and notification routing. The feature defaults
to disabled. The tests used synthetic sessions and PostgreSQL fixtures.
No SMS, email, external provider, production mutation, or remediation
restart was part of this change.

The migration uses a standalone sequence number. Reconcile it before
cumulative integration and rerun upgrade and restore with the resolved
ledger. An approved rollback to an earlier runtime needs a compatible
application revision or coordinated restore because runtime readiness
checks exact migration history.
